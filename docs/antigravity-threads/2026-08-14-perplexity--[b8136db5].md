Short answer

Yes, it's technically buildable — Jules VMs do have network egress and can run shell/curl commands, and a single task can occupy its VM for a good chunk of a session before timing out. But this specific design is *more* likely to trip abuse detection than the ideas you discussed before, not less, because it deliberately builds a bot-like control loop that fetches remote instructions and keeps a VM "alive" for the sole purpose of dodging the daily task counter.

Why it "works" mechanically

Jules limits are counted per **task**, not per compute-minute or token — free tier caps at 15 tasks/24h, Pro at ~100, Ultra at 300, with separate concurrency caps. Since each Jules task spins up its own cloud VM with real network access, a task whose instructions are "poll this endpoint every 5 minutes for new work" would indeed let you cram many logically distinct micro-tasks into the wall-clock budget of one task slot. That's the entire appeal: you're not creating new tasks, you're stretching one task's runtime to do the work of many.

Where context bloat actually bites

This is the real technical constraint, and it's serious:

Every curl response, every micro-task's tool calls, file reads, and command outputs accumulate in the *same* conversation context for the life of that one task — there's no natural reset point the way there is between separate tasks. Tool-result accumulation is consistently cited as the dominant driver of context bloat, with tool outputs alone sometimes reaching 80%+ of total context in long-running loops.
particula

As that context grows, you get quadratic cost per turn (re-processing a growing history every inference step), rising latency, and "lost in the middle" reasoning degradation where the model starts ignoring or misapplying instructions buried earlier in the transcript.

Without an explicit compaction/summarization step (trim or offload old tool results, keep only a structured summary of "done/pending" state), by task hour 1.5–2 the agent's judgment on new micro-tasks would likely be noticeably worse than a fresh task would produce, even though nothing has technically "failed".

Does it trip the T&S wires — and is it worse than before?

I don't have your earlier conversation in front of me to compare point-by-point, but on the specifics you've described here, this design adds a signal that's arguably more suspicious than simply running long single tasks:

**Sustained fixed-interval outbound polling.** A process that curls the same external endpoint every 5 minutes for up to 2 hours is a textbook bot/scheduler fingerprint — it's the kind of periodicity anomaly-detection systems are specifically built to flag, independent of what the payload contains.

**Remote instruction injection mid-task.** Having the agent fetch "new work" from an external server *during* task execution means the task's behavior is no longer determined by the original task description alone — it's being steered live by your infrastructure. That pattern overlaps heavily with what prompt-injection/remote-control abuse heuristics look for, since from Google's side it's indistinguishable from a malicious actor using the agent as a proxy execution engine.

**Explicit intent to bypass a quota.** The stated goal is literally to route around the daily task cap by making one task masquerade as many. Jules' Generative AI Prohibited Use Policy and its terms-of-service addendum govern exactly this kind of usage-limit circumvention; abuse review isn't just pattern-matching on API calls, it also weighs stated/inferable intent, and "I want to avoid the 15/100/300 task ceiling" is about as clear an intent signal as you can generate.
policies.google

**Resource-exhaustion optics.** Google explicitly frames task/concurrency limits as protecting VM stability and preventing "overuse or abuse". A task that pins a VM open for the maximum allowed session length specifically to maximize throughput per task-slot looks, from the platform's side, exactly like the overuse pattern those limits exist to stop — even if each individual micro-task is benign.
kdnuggets

Practical takeaway

If your actual goal is "get more real work done per day without spinning up dozens of separate tasks," the safer version of this idea is: front-load a single task with a well-scoped batch of related sub-goals in the initial prompt (a checklist Jules works through sequentially), rather than an open-ended curl/sleep loop pulling live instructions from your server. That gets you most of the throughput benefit, avoids the periodic-network-polling bot signature, and gives you a natural place to insert your own context-compaction (summarize each completed sub-goal before moving to the next) instead of letting the whole session's history snowball for two hours straight.
