## Gemini

Dealing with a Mac that refuses to sleep is usually down to a "power assertion"—a process or hardware flag telling macOS that it needs to stay awake to finish a task.


Here is how to track down the culprit using the Terminal and Activity Monitor.


1. Check for Active Power Assertions
The most direct way to see what is keeping your Mac awake is via the Terminal. Open Terminal and run the following command:


pmset -g assertions


Look for the section titled Listing Summary. You want to check the values for:



* PreventUserIdleSystemSleep: If this is 1, a process is actively stopping sleep.

* UserIsActive: This should be 0 if you aren't touching the Mac.


Scroll down to the bottom of the output to see the specific process names (e.g., coreaudiod, hidd, or a specific app like zoom.us) responsible for these assertions.


2. Use Activity Monitor
If you prefer a visual interface, Activity Monitor has a hidden column specifically for this:



* Open Activity Monitor (via Raycast or Spotlight).

* Click on the Energy tab.

* Right-click any column header (like "Process Name") and ensure Preventing Sleep is checked.

* Click that column to sort by "Yes." This will immediately highlight any app currently blocking your Mac from sleeping.


3. Review Wake Reasons
To see why your Mac woke up after it managed to sleep, run this command:


log show --style syslog --last 24h | grep -i "Wake reason"


This will list the hardware or software triggers from the last day. Common reasons include:



* RTC (Real Time Clock): Usually maintenance tasks or "Wake for network access."

* USB/HID: A mouse, keyboard, or even a slight vibration moving a high-sensitivity mouse.

* EHC/XHC: External USB devices or hubs.


4. Common System Settings to Toggle
If no specific app is showing up, check these system-level culprits:



* Wake for Network Access: Go to System Settings > Battery (or Energy Saver) > Options. Disable "Wake for network access" to prevent the Mac from waking up for background syncs.

* External Peripherals: If you use a USB-C dock or hub, try disconnecting it. Some hubs "leak" power or send keep-awake signals that prevent the system from entering a low-power state.

* Print Queue: Check your print queue in System Settings > Printers & Scanners. A stuck print job is a notorious but often overlooked reason for sleep prevention.



Since you use Keyboard Maestro, it’s also worth checking if any of your macros have a "Prevent system from sleeping" action currently active or stuck in a loop.

## Gemini

The pmset output reveals the specific culprit and several secondary factors keeping your Mac awake.


The Primary Offender: Electron (PID 46714)
The smoking gun is this line:
pid 46714(Electron): [0x0004df9800019928] 29:35:46 NoIdleSleepAssertion named: "Electron"


An Electron-based app has been holding a "NoIdleSleep" assertion for nearly 30 hours. Since "Electron" is a framework, this could be one of several apps. Common ones include:



* VS Code (often happens if a terminal process or debugger is still running).

* Discord (usually if you're in a voice channel or a video is "playing" in a tab).

* Slack or Obsidian.

* WhatsApp or Spotify.


To find exactly which app it is:
Run this in Terminal: ps -p 46714
This will give you the path to the actual application associated with that Process ID. Once identified, quit that app and your Mac should be able to idle to sleep.



Secondary Observations

* Karabiner-Elements (PID 173): You’ll notice UserIsActive is being triggered by Karabiner DriverKit VirtualHIDKeyboard. This is normal for your setup—it essentially means the system sees your remapped keyboard activity as "user input." However, if this triggers when you aren't touching the keys, it could suggest a stuck macro or a virtual "keep-alive" signal.

* Handoff (sharingd): sharingd is holding a brief assertion for Handoff. This is usually transient and shouldn't prevent sleep long-term, but it shows your Mac is currently communicating with your other Apple devices.

* USB Hub & Peripherals: Your Kernel Assertions show a heavy USB load, including an iRig Pre HD and a USB Audio CODEC. Audio interfaces are notorious for preventing sleep if the driver thinks an audio stream is "active," even if no sound is playing.


Immediate Fixes

* Kill the Electron app: After identifying it with ps -p 46714, force quit it.

* Toggle the Display Delay: powerd is currently delaying the display off by 70 seconds. If you close your laptop lid (if applicable) or wait for that timer, see if the InternalPreventDisplaySleep disappears.

* Check the iRig: Since you have audio gear connected, ensure no DAW (like Logic or Ableton) or browser tab with a microphone/input request is open, as the iRig Pre HD is currently registered as an active external device.
