## Gemini

If it says supported=false, that means "wakeLock" in navigator is returning false.


On an iPad, there are only three reasons why the standard navigator.wakeLock API will evaluate to false:


1. You are running an older version of iPadOS (or in a PWA container prior to 18.4)
Double-check your exact iPadOS version in Settings > General > About > iOS Version.



* If testing in standard Safari: The API requires iOS/iPadOS 16.4 or later.

* If testing as an installed Home Screen PWA: The API requires iOS/iPadOS 18.4 or later. If your iPad is on 18.3 or below, the API is entirely stripped from the PWA container environment, meaning "wakeLock" in navigator will be false.


2. You are not using HTTPS (or Localhost)
The Wake Lock API is explicitly restricted to Secure Contexts. If your Vite dev server is exposed over your local network and you are accessing it on your iPad via an IP address like [http://192.168.1.](http://192.168.1.)X:5173, Safari will completely disable the API.



* http://localhost:5173 is considered secure (but you can't type "localhost" on an iPad to reach your computer).

* [http://192.168.1.](http://192.168.1.)X:5173 is not considered secure.


The Fix: You need to force your Vite dev server to use HTTPS.



* Install the basic SSL plugin for Vite:
npm i -D @vitejs/plugin-basic-ssl



* Add it to your vite.config.ts:


   import basicSsl from '@vitejs/plugin-basic-ssl';

   export default defineConfig({
     plugins: [
       basicSsl(),
       // ... your other plugins like VitePWA
     ]
   });


* Restart your dev server and access the app on your iPad using [https://192.168.1.](https://192.168.1.)X:5173. Safari will warn you about an untrusted certificate; just bypass the warning, and the API will suddenly exist.


3. You are using a non-Safari browser app
If you are testing this inside the Google Chrome, Firefox, or Opera apps downloaded from the App Store on iPadOS, Apple restricts those browsers to older rendering architectures that do not expose the Wake Lock API. It must be tested inside native Safari or the installed PWA generated by Safari.

## Gemini

Switching your Vite dev server to HTTPS changes how local network discovery behaves, which is likely why matt.local suddenly stopped resolving or connecting.


When you use HTTPS, a few things break the standard [http://matt.local:5173](http://matt.local:5173) workflow. Here is how to fix it:


1. The Explicit Protocol Prefix
Because you are using a self-signed certificate now, your iPad will refuse to connect if you just type matt.local:5173 into the address bar. Safari will default to trying HTTP first, get confused by the SSL handshake, and drop the connection.


You must explicitly type the https:// prefix:


https://matt.local:5173

2. Vite Might Not Be Listening on the Network
By default, Vite often only exposes the dev server to localhost (your Mac). When you added the SSL plugin or restarted the server, it might have dropped the local network bridge.


Check your terminal where Vite is running. Does it list a Network URL?


  ➜  Local:   https://localhost:5173/
  ➜  Network: use --host to expose

If it says use --host to expose, your iPad won't be able to find it anymore.


The Fix: Update your package.json dev script to include the host flag:


"scripts": {
  "dev": "vite --host"
}

Or temporarily run npm run dev -- --host. This forces Vite to bind to your local IP address.


3. mDNS / Bonjour Dropping the Connection
Local hostnames like matt.local rely on a protocol called mDNS (Bonjour). It is notoriously finicky when switching security contexts or when an apple device sleeps.


If [https://matt.local:5173](https://matt.local:5173) still gives you a generic "Cannot Connect to Server" error, bypass the hostname entirely and use the raw local IP address that Vite prints in your terminal when you use the --host flag:


https://192.168.X.X:5173

What to expect when it connects:
The very first time you hit the HTTPS version on your iPad, Safari will display a scary-looking "This Connection Is Not Private" warning page.


Don't worry—this is normal for local development. Tap Advanced at the bottom, and then tap Proceed to website (unsafe). Once you bypass that hurdle, your app will load, and the Wake Lock API will be completely active.

## Gemini

To disable user zooming on mobile devices, you need to add specific parameters to the viewport meta tag in your index.html <head>.


<meta name="viewport" content="width=device-width, initial-scale=1.0, maximum-scale=1.0, user-scalable=no">

What these properties mean:

* width=device-width, initial-scale=1.0: Standard properties to ensure the site renders at the correct scale relative to the device's screen size.

* maximum-scale=1.0: Prevents the browser from scaling the page up beyond its default 100% size.

* user-scalable=no: Explicitly tells the browser to ignore pinch-to-zoom gestures and double-tap zooming.



⚠️ Crucial Caveat for iOS / Safari
Starting with iOS 10, Apple deliberately chose to ignore user-scalable=no and maximum-scale=1.0 in standard Safari to improve accessibility for visually impaired users.


However, because you are building a PWA, there are two ways around this:



* It works when installed: If your web app is installed to the Home Screen as a standalone PWA, iOS will honor the user-scalable=no tag, and zooming will be disabled within the PWA container.

* The CSS Fix (for inputs): On mobile Safari, the browser will automatically zoom in if a text input or form field has a font size smaller than 16px. To prevent this annoying auto-zoom behavior without breaking accessibility, make sure your input fields have a font size of at least 16px in your CSS:
input, select, textarea {
  font-size: 16px;
}
