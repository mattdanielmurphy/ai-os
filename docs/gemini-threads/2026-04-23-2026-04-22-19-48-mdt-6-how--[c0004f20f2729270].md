## Gemini

In Antigravity, increasing the Model Context Protocol (MCP) server timeout requires adding a timeout property directly to the specific server configuration within your settings file.


By default, many MCP clients set a standard timeout (often 10 or 30 seconds). If your proxima server is handling heavy computations or large datasets, you can extend this by modifying your JSON structure as follows:


Configuration Update
{
  "mcpServers": {
    "proxima": {
      "command": "/Users/matthewmurphy/.nvm/node-auto",
      "args": [
        "/Users/matthewmurphy/external-projects/Proxima/src/mcp-server-v3.js"
      ],
      "timeout": 60000
    }
  }
}

Key Details

* Unit of Measurement: The timeout is typically defined in milliseconds. In the example above, 60000 sets the limit to 60 seconds.

* Placement: Ensure the timeout key is inside the object for the specific server (proxima), sibling to command and args.

* Restart: After saving the changes to your configuration file, you must restart the Antigravity environment for the new timeout settings to take effect.


If you continue to see "connection closed" or "request timed out" errors after increasing this value, it may be worth checking the server-side logs for the mcp-server-v3.js file to ensure the process isn't crashing before the timeout is reached.

## Gemini

If Antigravity is rejecting the timeout property in your mcp_config.json, it is likely because Antigravity (unlike some other MCP clients) uses a strict schema for that file that doesn't include a client-side timeout override per server.


Since you've already bumped the timeout on the Proxima side, the bottleneck is almost certainly Antigravity's internal 60-second hard cap for tool calls. Here is how to work around it:


1. The "Progress Notification" Trick (Recommended)
Antigravity's underlying MCP client (based on the standard TypeScript SDK) usually respects progress updates. If a tool sends a progress notification, the client-side timeout often resets.


In your mcp-server-v3.js, ensure your tool call implementation supports and sends progress tokens.



* Server side: When you receive a progressToken in the tool request, send a notifications/progress message every 30–45 seconds.

* Effect: This "pings" Antigravity, telling it the process is still alive, which can prevent the 60s hammer from falling.


2. Move to an Async "Job" Pattern
If the task consistently takes 10 minutes, standard request-response patterns are prone to failure in most IDEs. The more robust way to handle this in Antigravity is:



* Start Tool: The agent calls start_proxima_task.

* Immediate Return: The server returns a job_id immediately (e.g., "Task started, check back in a bit").

* Poll Tool: The agent then uses a second tool, check_proxima_status, to poll for the result.


3. Check for the Hidden env Setting
Some users have had success forcing environment variables into the config that the underlying Node process picks up, though this is "undocumented" for Antigravity specifically:


"proxima": {
  "command": "/Users/matthewmurphy/.nvm/node-auto",
  "args": ["/Users/matthewmurphy/external-projects/Proxima/src/mcp-server-v3.js"],
  "env": {
    "MCP_REQUEST_TIMEOUT": "600000" 
  }
}

(Note: This only works if your server code specifically reads this env var to set its own internal transport timeouts, but it won't hurt to try.)


Why is this happening?
Antigravity's Agent Manager is designed to prevent "zombie" tools from hanging the entire UI. It currently enforces a strict timeout to ensure the agent doesn't get stuck in a loop. If timeout is rejected as an "unallowed property," it confirms the IDE's schema is locked down for now.
