Here is the breakdown of local vs. worktree in git-backed agentic environments, and why parallel development doesn't have to be a nightmare.



Local vs. Worktree
In standard Git, you usually have one working directory associated with your repository. However, Git allows you to split these concepts up:



* Local (Your Main Working Directory): This is your primary sandbox. It’s the directory where you are currently checked out to a specific branch, making manual edits, and running your local build or test suite.

* Worktree (Linked Working Trees): A Git feature (git worktree) that lets you have multiple working directories attached to the same repository simultaneously, each checked out to a different branch.


Instead of constantly running git stash, switching branches, and popping the stash just to look at or edit something else, you can spin up a separate folder (a worktree) that points to the exact same .git history but is checked out to feature-b while your main folder stays on feature-a.



Using Worktrees with AI Agents
When utilizing coding harnesses or AI agents, worktrees become incredibly useful for isolation rather than just "editing in tandem."


If you want an agent to explore a refactor, fix a bug, or write a test suite, assigning it to a dedicated worktree means:



* Zero Pollution: The agent operates in its own isolated directory. It won't overwrite your uncommitted local files or break your active build.

* Parallel Execution: You can have an agent running tests or generating code in worktree-A while you continue working uninterrupted in your main local workspace.



Is Parallel Always Worse Than Linear?
Your intuition about merge conflicts is spot-on for classic manual development, but the math changes slightly when agents are involved.


If two agents are touching the exact same lines of code simultaneously, yes, linear is superior. Parallelizing edits on the same file leads to messy conflict resolution that agents often struggle to handle cleanly.


However, parallel development via worktrees shines when the tasks are orthogonal (independent):



* Task A (Agent 1): Writes unit tests for a utility file in worktree-1.

* Task B (Agent 2): Updates documentation or changes CSS layout files in worktree-2.

* Task C (You): Work on core business logic in your local directory.


Because these tasks target different files or modules, they can be merged back into the main branch automatically without structural conflicts.


The Strategy

* Use Linear Execution when tasks are highly interdependent or touch the same files. Let the agent finish, commit, and then issue the next command.

* Use Parallel Worktrees when splitting up decoupled tasks (e.g., frontend styling vs. backend migrations), allowing you to maximize throughput without bottlenecking your own local workflow.


Are you planning to have multiple agents target the same codebase simultaneously, or are you looking to offload background tasks while you write code?
