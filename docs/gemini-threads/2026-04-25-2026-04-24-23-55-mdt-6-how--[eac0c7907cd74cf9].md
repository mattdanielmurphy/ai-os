To list all available formats for a specific video using yt-dlp, use the uppercase -F flag:


yt-dlp -F "URL"

Breakdown of the output
When you run this command, yt-dlp will output a table that looks something like this:





































IDEXTRESOLUTIONFPSFILESIZETBRVCODECACODEC137mp41920x10803050.50MiB2500kavc1.640028video only251webmaudio only3.20MiB128kaudio onlyopus

* ID: The unique format code. You’ll use this number later if you want to download a specific version.

* EXT: The file extension (mp4, webm, etc.).

* RESOLUTION/FPS: The video quality and frames per second.

* VCODEC/ACODEC: Indicates if the stream is "video only," "audio only," or a combined "muxed" file.



Pro-Tips for Format Selection
Once you’ve found the formats you want from the list, you can download them specifically using the lowercase -f flag.



* Download a specific ID:
yt-dlp -f 137 "URL"



* Combine specific video and audio:
If you want the 1080p video (ID 137) and the high-quality Opus audio (ID 251) merged into one file:
yt-dlp -f 137+251 "URL"



* Fastest way to check:
If you are using yt-dlp in a script or just want the info without waiting for the full metadata check, you can use --simulate:
yt-dlp -F --simulate "URL"

## Gemini

The absence of yt-dlp on npm (Node Package Manager) primarily stems from the fact that it is a Python-based application, not a JavaScript or Node.js one.


While some Python tools are occasionally wrapped in shim packages for npm to make them accessible to Node developers, the yt-dlp team focuses on native distribution methods that align with its codebase and dependencies.


Here are the specific reasons why you won't find an official version there:


1. Language Mismatch
yt-dlp is written in Python. npm is designed for JavaScript/TypeScript packages. To host it on npm, the developers would have to maintain a "wrapper" that essentially just downloads the Python binary or source, which adds unnecessary complexity and potential security risks.


2. Dependency Management
yt-dlp often requires FFmpeg or ffprobe for merging video and audio streams. Python-centric managers like pip or system managers like brew and apt are better equipped to handle these types of multi-language binary dependencies than npm.


3. Preferred Distribution Channels
As seen in the Installation Wiki, the project prioritizes:



* PyPI (pip): The native home for Python packages.

* Standalone Binaries: For users who don't want to manage a Python environment.

* System Package Managers: Like Homebrew, Scoop, or Winget for OS-level integration.


How to use it in a Node project
If you are building a Node.js application and need yt-dlp functionality, the standard approach is to:



* Install yt-dlp on your system (e.g., via brew install yt-dlp or pip install yt-dlp).

* Use the Node.js child_process module to run it as a command-line tool from your code.

* Alternatively, use a community-maintained wrapper like yt-dlp-exec, which handles the execution logic for you.

## Gemini

The reason yt-dlp isn't a Node package is a mix of historical momentum, technical trade-offs, and the specific way "Node versions" of tools like FFmpeg actually work.


1. The "Node version" of FFmpeg is a bit of a mirage
When you see ffmpeg on npm (like fluent-ffmpeg), it isn't actually a rewrite of FFmpeg in JavaScript.



* The CLI Wrapper: Most npm packages are just "wrappers." They still require the actual C++ FFmpeg binary to be installed on your system. They just provide a nice JavaScript syntax to send commands to it.

* WebAssembly (WASM): There is a version called @ffmpeg/ffmpeg that runs in the browser or Node using WebAssembly. While impressive, it is significantly slower than the native version and isn't practical for a heavy-duty tool like yt-dlp that needs to handle massive 4K video files efficiently.


2. Why Python? (The 20-Year Legacy)
yt-dlp didn’t start from scratch. It is a fork of youtube-dl, which was created in 2006.



* Historical Choice: In 2006, Python was the king of "glue code"—the language used to talk to various websites, parse text, and run other programs. Node.js didn't even exist until 2009.

* Massive Library: yt-dlp contains hundreds of "extractors" (scripts that know how to scrape specific sites). Moving to TypeScript would mean rewriting hundreds of thousands of lines of code that already work perfectly.

* The "Glue" Factor: Python excels at handling system-level tasks (like running FFmpeg) and complex networking, which is the core of what yt-dlp does.


3. Are things shifting to TypeScript?
Yes and no. While TypeScript has recently overtaken Python as the #1 language on GitHub by contributor count, the shift is domain-specific:
































DomainPreferred Language (2026)Why?Web & App FrontendsTypeScriptAbsolute dominance. Types prevent 38% of production bugs.Backend APIsTypeScript / GoFast execution and great developer tooling.AI & Data SciencePythonStill the undisputed leader due to libraries like PyTorch and NumPy.System Tools (CLI)Python / RustPython for ease of contribution; Rust for speed.
The "Plot Twist" in 2026
Interestingly, yt-dlp is actually moving toward JavaScript right now, but not by rewriting the whole app.


Because YouTube has made its site more complex, yt-dlp now requires a JavaScript runtime (like Deno, Node.js, or Bun) to be installed on your system to help it solve "JavaScript challenges" from YouTube's servers. It's becoming a hybrid: Python for the logic, and Node/Deno for the heavy lifting on the web.


Summary: You won't find a native JS version because the Python version is a 20-year-old masterpiece of web scraping that is too massive to port, but it's increasingly relying on the Node ecosystem to stay functional.

## Gemini

Correct. The output shows standard 1080p options (ID 137, 248, and 399), but it does not list 1080p Premium (enhanced bitrate).


"1080p Premium" is typically only available to YouTube Premium subscribers. Since yt-dlp is accessing the video as a guest/unauthenticated user by default, it only sees the publicly available streams.


How to see and download Premium formats
To access those formats, you need to pass your browser cookies to yt-dlp so it can verify your Premium status.



* Extract your cookies: Use a browser extension (like "Get cookies.txt LOCALLY") to export your cookies, or simply point yt-dlp to your browser.

* Run the command with cookies:
yt-dlp --cookies-from-browser chrome -F "https://youtu.be/huB67xaX47A"

(Replace chrome with your browser: firefox, safari, edge, etc.)


If you have an active subscription, you should see a new entry in the list, often marked with a higher TBR (Total Bitrate) than the standard 1080p streams.


Notes on the current list:

* Standard 1080p (ID 137): This is the H.264 version at ~1810k bitrate.

* Standard 1080p (ID 399): This is the AV1 version at ~970k bitrate (more efficient, but lower raw bitrate).

* Premium: Usually appears as a separate format ID with a significantly higher bitrate (often 3000k–4000k+ for 1080p).

## Gemini

You aren't imagining things. There was a period where yt-dlp could "trick" YouTube into serving the 1080p Premium formats even if you didn't have a paid account.


This was possible by using specific Extractor Arguments that made the request look like it was coming from an iOS device. At the time, YouTube’s iOS API didn't strictly gate those high-bitrate streams behind a subscription check for every request.


The "iOS Trick" (Now largely patched)
In the past, you could run this to see the "hidden" formats (often format IDs like 616 or 617):


yt-dlp -F --extractor-args "youtube:player_client=ios" "URL"

Why it doesn't work anymore
Over the last year, YouTube has significantly tightened its API security:



* Signature Changes: YouTube now requires a valid signature (frequently referred to as "PoToken" or "Visitor Data") that links a request to a legitimate session.

* Server-Side Gating: The iOS client now enforces the Premium check on the server side. If the account (or guest session) doesn't have the Premium flag, the server simply returns a 403 Forbidden error or omits the format from the manifest entirely.

* Deno Integration: You may have noticed your yt-dlp output mentions "Solving JS challenges using deno." This is part of the ongoing "arms race" to keep standard downloads working at all, let alone the Premium ones.


Is there any workaround?
If you're after the best possible quality without a Premium account, your best bet is to look for a 1440p (2K) or 2160p (4K) version of the video if it exists.


YouTube’s standard 1440p stream (VP9 or AV1) actually has a higher bitrate and better visual fidelity than the "1080p Premium" stream. If the video was only uploaded in 1080p, you are unfortunately capped at the standard bitrates (ID 137 or 399) unless you provide valid Premium cookies.



Note: If you do have a friend with Premium, you could theoretically use their cookies.txt file, but YouTube is increasingly aggressive about flagging accounts that share cookies across different IP addresses.

## Gemini

Technically, using her cookies from the same external IP significantly lowers the risk of a "suspicious activity" flag compared to using them on a server in another country. However, there are still a few hurdles and risks to consider with how YouTube tracks sessions in 2026.


The Security Hurdle: App-Bound Encryption
Since you're on macOS, you'll run into a specific issue if you try to pull cookies directly from her browser on a different user account or machine. Chrome and other Chromium browsers now use App-Bound Encryption.



* The Problem: The encryption key used to protect browser cookies is tied to the specific OS user profile and the browser binary.

* The Result: Even if you copy her Chrome "Cookies" database file to your folder, yt-dlp won't be able to decrypt it.


How to do it safely
If you want to use her Premium status, the most reliable way is to export the cookies to a standalone text file from her session:



* On her machine/profile: Use a "Netscape formatted" cookie exporter or yt-dlp itself to generate a file:
yt-dlp --cookies-from-browser chrome --cookies my_mom_cookies.txt --simulate "https://www.youtube.com"

(This creates a my_mom_cookies.txt file in the current directory.)

* On your machine: Move that text file to your project folder and reference it:
yt-dlp --cookies my_mom_cookies.txt -F "URL"




The Risks (The "Shared IP" factor)
While sharing an external IP makes you look like a single household (which is generally allowed), YouTube's "InnerTube" API tracks more than just IP:



* Device Fingerprinting: They can see that the request is coming from a different machine (different OS version, hardware specs, etc.) than the one she usually uses to watch videos.

* Simultaneous Streams: If she is watching Premium content in the living room while you are using her cookies to download at high speed via yt-dlp, it can trigger a "too many concurrent sessions" block or force a log-out on her end.

* The "Slow & Steady" Rule: To avoid flagging her account, avoid mass-downloading. If you're just grabbing a few videos in 1080p Premium, you'll likely be fine.


Better Alternative?
If the goal is purely visual quality, check if the video is available in 1440p (2K).
YouTube does not gate 1440p or 4K behind Premium—only the "Enhanced Bitrate" 1080p. A standard 1440p stream (VP9/AV1) almost always has a higher bitrate and better clarity than a 1080p Premium stream anyway.

It really is. Seeing "Netscape" in a terminal in 2026 feels like finding a floppy disk in a Tesla. It’s a total relic from the 90s browser wars, but it’s essentially the "universal language" for cookie files because it’s a simple, tab-separated plain text format.


Modern browsers use encrypted SQLite databases to keep your data safe from other apps, but yt-dlp and curl still rely on that old-school text structure to read session data without needing to hook into the browser's actual engine.


Why it’s still the standard:

* Portability: It’s just text. You can copy-paste it into a .txt file, and any CLI tool can parse it in milliseconds.

* No Encryption Hassle: Since you've already decrypted the cookies by exporting them while logged in, the text file doesn't care about macOS Keychain or App-Bound Encryption.

* Simple Logic: It just lists the domain, expiration, name, and value. No proprietary bloat.
