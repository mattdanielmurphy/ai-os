## Gemini

For optimal readability, the ideal line length is generally 45 to 75 characters per line (including spaces). This is often considered the typographic "sweet spot" because it prevents the eye from getting too tired scanning long lines or breaking rhythm with frequent jumps on short ones.


When translating this rule of thumb into rem units (assuming the standard browser default base of $1\text{rem} = 16\text{px}$), the best max-width range is 30rem to 45rem.


Here is how that breaks down based on your target layout:


The Breakdown

* 30rem to 35rem (~480px – 560px): Yields a tighter, highly scannable line length (around 45–55 characters). This works incredibly well for multi-column layouts, side blogs, or denser technical documentation where quick scanning is a priority.

* 38rem to 40rem (~608px – 640px): The absolute sweet spot for long-form reading (around 60–70 characters). It hits the exact middle of the ideal range and feels natural for essays, articles, and documentation.

* 45rem (~720px): The upper limit for standard body text (around 75–80 characters). If you go much wider than this without increasing the font-size or line-height, the text can begin to feel like a wall.



Implementation Tip using ch
While rem is excellent for keeping your layout bound to the root font scale, you can also use the ch (character) unit for maximum precision. 1ch is equal to the width of the "0" glyph in your chosen typeface.


.article-body {
  /* Safely caps the width to roughly 65 characters wide */
  max-width: 65ch; 
  width: 100%;
}

If you stick with rem, setting your main text container to max-width: 40rem; is an excellent, bulletproof baseline for long-form reading.

## Gemini

This is a common issue with WebKit-based apps on macOS. By default, WebKit (which Tauri uses via wkwebview) can sometimes force scrollbars to remain visible regardless of system preferences, and standard scrollbar styling doesn't automatically inherit app dark mode changes seamlessly unless explicitly configured.


You can fix this entirely using CSS.



1. The CSS Solution
Add the following styles to your global CSS file (e.g., index.css or style.css). This targets WebKit's scrollbar pseudo-elements to force the "overlay" behavior and apply discrete, dark-mode-friendly colors.


/* Ensure the body and containers handle overflow correctly */
html, body {
  overflow: auto;
}

/* 1. Force the scrollbar to be discrete and use custom dimensions */
::-webkit-scrollbar {
  width: 8px;  /* Width of vertical scrollbar */
  height: 8px; /* Height of horizontal scrollbar */
  background: transparent; /* Makes the track invisible until hovered */
}

/* 2. The Scrollbar Track (the background) */
::-webkit-scrollbar-track {
  background: transparent;
}

/* 3. The Scrollbar Thumb (the draggable handle) */
::-webkit-scrollbar-thumb {
  background: rgba(255, 255, 255, 0.2); /* Semi-transparent white for dark mode */
  border-radius: 4px; /* Fully rounded edges */
  border: 2px solid transparent; /* Acts as padding inside the track */
  background-clip: padding-box; /* Ensures the border doesn't overlap the background */
}

/* 4. Hover effect to make it slightly more visible when interacting */
::-webkit-scrollbar-thumb:hover {
  background: rgba(255, 255, 255, 0.4);
  border: 2px solid transparent;
  background-clip: padding-box;
}

/* 5. Optional: Light mode overrides if your app supports both */
@media (prefers-color-scheme: light) {
  ::-webkit-scrollbar-thumb {
    background: rgba(0, 0, 0, 0.2);
  }
  ::-webkit-scrollbar-thumb:hover {
    background: rgba(0, 0, 0, 0.4);
  }
}


2. Why This Works

* background-clip: padding-box: This is the trick to getting that slim, native macOS look. It creates an invisible padding boundary around the thumb so it looks discrete and floating, rather than filling the entire 8px width.

* rgba Colors: By using transparent alpha channels (rgba(255, 255, 255, 0.2)), the scrollbar naturally blends into whatever background color your webview is currently rendering.



3. Check macOS System Settings
If the scrollbars still persist after applying the CSS, check your macOS system-wide setting under System Settings > Appearance > Show scroll bars.


If it is set to Always, macOS overrides webview behaviors and forces them to stay visible. Setting it to Automatically based on mouse or trackpad or When scrolling will let your new CSS auto-hide properly when idle.

Ah, if they are on specific elements with overflow: auto or overflow: scroll, WebKit handles container elements a bit more rigidly than the root body.


To completely tame container-level scrollbars, you need to explicitly strip the default system appearance using -webkit-appearance: none and ensure the container's parent isn't forcing a layout rule that interferes with WebKit's rendering engine.


Here is the updated CSS tailored specifically for individual elements.



The Container-Specific Fix
Replace or complement your previous styles with this block. It forces the targeted containers to drop native styling and adopt the overlay behavior:


/* Target any element with overflow control */
.your-scrollable-container {
  overflow: auto;
  
  /* Disables default platform rendering behaviors */
  -webkit-appearance: none; 
}

/* Force custom scrollbar properties on the element */
.your-scrollable-container::-webkit-scrollbar {
  width: 8px !important;
  height: 8px !important;
  background: transparent !important;
}

.your-scrollable-container::-webkit-scrollbar-track {
  background: transparent !important;
}

.your-scrollable-container::-webkit-scrollbar-thumb {
  background: rgba(255, 255, 255, 0.2) !important;
  border-radius: 20px !important; /* High radius ensures a pill shape */
  border: 2px solid transparent !important;
  background-clip: padding-box !important;
}

.your-scrollable-container::-webkit-scrollbar-thumb:hover {
  background: rgba(255, 255, 255, 0.4) !important;
}

/* Light mode support */
@media (prefers-color-scheme: light) {
  .your-scrollable-container::-webkit-scrollbar-thumb {
    background: rgba(0, 0, 0, 0.2) !important;
  }
  .your-scrollable-container::-webkit-scrollbar-thumb:hover {
    background: rgba(0, 0, 0, 0.4) !important;
  }
}


Two Critical Details for Individual Elements
If the above still shows persistent track bars, check for these two hidden WebKit traits:


1. Avoid overflow: scroll
Ensure you are using overflow: auto; on the element. If you use overflow: scroll;, WebKit is forced by spec to permanently reserve space for the scrollbar track, meaning a blank bar will stay visible even when there is nothing to scroll.


2. The Global CSS Scope
If your container lives inside a shadow DOM component (like a custom element or certain framework components), the ::-webkit-scrollbar pseudo-elements might not be penetrating it. Ensure this CSS is injected into the same scope as the element, or apply it universally by changing .your-scrollable-container::-webkit-scrollbar to *::-webkit-scrollbar to blanket every element in the app.
