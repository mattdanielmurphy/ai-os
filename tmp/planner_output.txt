## Architectural Strategy

Change the morning flow from “minimum review → C&H reward → continue/finish choice” to “minimum review → C&H reward → automatic review of all remaining due cards → completion.” Separately, treat Telegram nudges as a **singleton** notification: replacing a nudge retires the previous one, and tapping “I’m up” retires the tapped nudge while resuming—not advancing—the saved morning stage.

### Preserve these existing semantics

- Morning stages remain centering → gratitude → minimum review → C&H reward → remaining review → completion.
- Only gratitude accepts free-text journal entries.
- Cards retain answer-before-rating behavior, cached choices, and reveal-answer fallback.
- The minimum remains configurable, with its existing default and counting rules unchanged.
- No due cards still counts as a maintained day and earns the reward.
- The reward remains separate, with the existing comic-image delivery and official-page fallback.
- Context Gate, reminder scheduling, awake-time timeout, and acknowledgment-based reminder suppression remain unchanged.
- “Automatically sends the next card” means after each accepted rating—not sending all cards at once or auto-answering them.

## 2. Data Structures & State Management

### Morning flow state

Reuse existing persisted fields where possible. The required logical state is:

| State | Contract |
|---|---|
| `flow_id` | Stable identifier for one morning sequence. |
| `stage` | Existing morning stage, with an unambiguous distinction between minimum review and post-reward draining. |
| `review_count` | Existing accepted-rating count; unchanged counting semantics. |
| `reward_status` | Existing persisted reward-delivery status, sufficient to avoid ordinary duplicate delivery. |
| `active_card_id` | Current unanswered/unrated card, if any. |
| `active_prompt_message_id` | Canonical interactive stage/card prompt; never implicitly overwritten by a disposable nudge. |
| `completed_at` | Existing terminal marker or equivalent. |

Prefer reusing the existing post-threshold stage rather than adding another enum value. If necessary, introduce `review_remaining`; retain compatibility with persisted legacy “continue/finish” state.

### Nudge state

Persist, per chat and active morning flow:

- `latest_nudge_message_id`
- An existing signal identifier or monotonic `nudge_generation`
- Acknowledged/reminders-disabled state
- Association with the relevant `flow_id`

Keep nudge identity distinct from the active card/stage prompt. If the current signal abstraction combines them, preserve that abstraction but add explicit roles so retiring a nudge cannot invalidate the active review callback.

### Concurrency and restart rules

- Serialize morning mutations per chat/flow using the existing dispatcher or lock.
- Protect persisted transitions against duplicate callbacks using existing transactional/idempotency machinery.
- On restart, restore the active card before selecting another.
- Do not use an in-memory-only list of remaining cards.
- No schema migration is required if existing state already expresses these contracts.

## 3. API / Interface Contracts

These signatures describe required responsibilities; adapt their names and types to the actual codebase.

```text
advance_morning_review(chat_id, flow_id) -> AdvanceResult
```

Returns one of:

- `awaiting_current_card`
- `card_sent`
- `completed`
- `delivery_failed`

It verifies the flow, preserves any pending card, queries the existing due selector, and either sends one card or completes.

```text
ensure_morning_reward(chat_id, flow_id) -> RewardResult
```

Uses the existing reward delivery/fallback path and persisted delivery guard. It must not re-award the reward after each subsequent rating.

```text
replace_morning_nudge(chat_id, flow_id) -> NudgeResult
```

Retires the previous nudge, sends one replacement, and records its identity without changing the saved morning stage.

```text
acknowledge_morning_nudge(chat_id, flow_id, message_id, signal_id)
    -> AcknowledgmentResult
```

Validates callback ownership, acknowledges the reminder, retires its message, disables repeats as currently defined, and resumes the saved stage without marking any stage complete.

```text
retire_nudge(chat_id, message_id) -> RetirementResult
```

Attempts deletion first. If deletion fails, removes its inline keyboard and replaces its text with a short inactive marker. A retirement failure must be observable; it must not silently create another actionable reminder.

Completion and rating helpers must retain their existing contracts for non-morning callers.

## 4. Logic Flow & Algorithms

### Review progression

```text
On entry to morning review:
    restore existing active card, if present
    otherwise evaluate existing minimum/no-due rules

On accepted card rating:
    validate callback belongs to current flow and active card
    apply the FSRS update exactly once
    update existing morning review count
    clear/retire the completed card using current behavior

    if minimum is now satisfied and reward has not been delivered:
        run existing C&H reward delivery/fallback

    if reward transition is satisfied under existing delivery semantics:
        advance_morning_review()
    otherwise:
        retain recoverable current state
```

```text
advance_morning_review():
    reject stale/completed flow
    if an active card is awaiting interaction:
        preserve/resume it
        return awaiting_current_card

    select next card using existing morning due-card eligibility
    if a due card exists:
        reserve its identity
        deliver it using existing answer-before-rating path
        persist its active prompt
        return card_sent

    complete the morning flow exactly once
    disable reminders and retire any remaining nudge
    return completed
```

Query due cards after each rating rather than draining a snapshot. If the existing selector considers a previously rated card due again, preserve that scheduling behavior. Completion occurs when that selector returns no eligible due card—not merely when every initially due card has been shown once.

Do not introduce delays, new card limits, or changes to minimum-count semantics.

### Nudge replacement

```text
On a scheduled reminder:
    apply existing schedule, Context Gate, and acknowledgment checks
    serialize against callbacks and other reminder sends
    retire previous tracked nudge
    if it cannot be deleted or made inactive:
        retain it and skip replacement; record failure
    otherwise:
        send one new nudge
        persist its identity and flow association
```

A retired fallback message may remain as an inactive marker, but only the latest nudge may remain visible as an actionable reminder.

### “I’m up”

```text
On callback:
    acknowledge Telegram callback promptly
    resolve and validate flow/signal/message identity
    retire the tapped nudge

    if callback is stale or flow is already complete:
        do not mutate a newer flow
        return

    disable further nudges under existing acknowledgment semantics
    clear matching nudge ownership only
    resume saved centering/gratitude/review stage
    preserve the current card and answer/reveal state
```

If existing acknowledgment resumes by editing the reminder itself, change that path: retire the reminder and restore/send the stage through the canonical morning-prompt mechanism instead.

### Legacy continue/finish buttons

- Stop generating continue/finish prompts.
- A legacy `continue` callback routes to automatic progression.
- A legacy `finish` callback must not prematurely complete a flow with due cards. Retire that obsolete choice prompt and resume progression.
- Completed or obsolete flow callbacks remain harmless.
- Preserve any independent cancellation command; do not reinterpret it as an obsolete finish button.

## 5. Error Handling & Edge Cases

- Duplicate ratings: no repeated FSRS updates, rewards, next-card sends, or completion.
- Card-send failure: retain a recoverable pending-card state; do not count it as reviewed or complete the flow.
- Reward failure: preserve existing failure/fallback semantics. Do not invent a new blocking policy; route into automatic progression where the old flow would have offered continue/finish.
- Nudge deletion unavailable: remove controls and mark inactive. If both operations fail, skip replacement rather than accumulate reminders.
- Nudge-send failure after retirement: leave no active nudge pointer; allow a later scheduled retry without changing the morning stage.
- Stale acknowledgment: retire the stale message but never acknowledge, finish, or rewind a newer flow.
- Reminder/acknowledgment race: serialize and recheck acknowledgment immediately before sending.
- Restart after rating: resume persisted progression without reapplying the rating.
- Crash during Telegram delivery: use existing outbound-delivery reconciliation if available. Do not claim exactly-once Telegram delivery from a database flag alone.
- Day rollover: preserve existing flow ownership and eligibility rules; an old nudge must not attach to the new morning flow.
- No due cards initially or after rating: reward and complete through the existing maintained-day path.
- Missing generated options: preserve reveal-answer fallback and avoid synchronous model generation.

### Acceptance criteria

- The threshold rating delivers the reward and then the next due card without another user choice.
- Every subsequent accepted rating sends exactly one next card or completes when none remain.
- No new continue/finish prompt appears.
- At most one actionable nudge exists; older nudges are deleted or visibly retired.
- “I’m up” retires its nudge, stops repeats, and restores the exact active stage without resetting card interaction state.
- Existing morning ordering, reward behavior, FSRS interaction, journaling boundaries, and non-morning reviews remain intact.
