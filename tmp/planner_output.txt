## Root Cause of "Half-Assed" Regressions

Electron/Chromium apps (which Antigravity is, per the `ai-os` context describing it as an editable VS Code–style webview harness) **destroy and recreate their AXUIElement tree on every re-render**. A naive re-implementation typically caches the raw `hs.axuielement` object, which silently goes stale the moment the chat UI re-renders (new message, streaming token, resize) — this is almost certainly why "half-assed" attempts stop working after the first success: they cache the *reference*, not a *recoverable path* to it, and have no fallback when the reference dies.

## 1. Architectural Strategy

Use a **three-tier resolution strategy**, attempted in order, with the result of tier 2/3 always re-cached for tier 1's next use:

1. **Tier 1 — Cached Path Replay (fast path).** Re-resolve a previously discovered element using a stored *structural path* (sequence of role+index steps from the window root), not the raw AX object. Validate liveness before acting.
2. **Tier 2 — Heuristic Targeted Search (medium path).** If the cached path fails to resolve or the resolved element fails validation (disabled, off-screen, wrong role), run a bounded, attribute-filtered search starting from the most likely subtree (e.g., last known parent container) instead of the whole window.
3. **Tier 3 — Full Intelligent Traversal (slow path, rare).** Full BFS/DFS from `AXWindow` root with role/subrole/description/position heuristics, depth and time limits, with the winning element's path immediately persisted to cache for tiers 1–2.

Critically, **AXPress the button directly** rather than only sending the `cmd+return` keystroke. Sending keystrokes assumes the input field has real OS-level focus and that the app's own keybinding is correctly wired; directly invoking `AXPress` on the resolved submit button is deterministic regardless of Electron's internal focus/keybinding state — this is very likely why the "original" was described as working "every time."

## 2. Data Structures & State Management

Module-level cache table, one entry per distinct app window (keyed by window ID, since Antigravity may have multiple windows/profiles open):

```
AntigravityCache = {
  [windowID] = {
    path        = { {role="AXGroup", index=2}, {role="AXGroup", index=0}, {role="AXButton", index=1} }, -- structural breadcrumb from AXWindow root
    axRef       = <hs.axuielement or nil>,   -- opportunistic hot cache, may be stale
    signature   = "AXButton|Submit|enabled",  -- role+title+state fingerprint used to validate a resolved element is the *right* one
    lastValidAt = <os.time() timestamp>,
    lastAppPID  = <pid>,
    failCount   = 0,  -- consecutive resolution failures; triggers full retraversal after threshold
  }
}
```

Persist `path`/`signature` (not `axRef`) to disk (`~/.hammerspoon/cache/antigravity_submit.json`) via `hs.json.encode`/`hs.settings.set` so the cache **survives Hammerspoon reloads**, not just app-session lifetime. This was very likely part of the "original" behavior — it "saved the button reference" durably, not just in RAM.

## 3. API / Interface Contracts

```lua
-- module: antigravity_submit.lua
local M = {}

-- Public entrypoint bound to the hotkey (e.g. cmd+enter)
function M.submit() end                     -- returns boolean success

-- Tier 1
function M.resolveFromCache(windowID) end   -- -> axuielement|nil, reason:string

-- Tier 2/3
function M.search(root, predicate, opts) end
-- opts = { maxDepth=12, timeoutSec=1.5, startNode=nil (subtree hint) }
-- predicate(node) -> boolean; used for role/title/subrole matching
-- returns axuielement|nil, pathTable|nil

-- Validation
function M.isElementValid(axRef, expectedSignature) end -- -> boolean
function M.signatureOf(axRef) end                        -- -> string fingerprint

-- Cache lifecycle
function M.cacheStore(windowID, pathTable, signature) end
function M.cacheInvalidate(windowID) end
function M.cacheLoadFromDisk() end
function M.cacheFlushToDisk() end

-- Path replay
function M.resolvePath(rootElement, pathTable) end -- -> axuielement|nil
```

Bind in `init.lua`:
```lua
hs.hotkey.bind({"cmd"}, "return", function() require("antigravity_submit").submit() end)
```

## 4. Logic Flow & Algorithm

```
function submit():
    win = frontmost Antigravity window
    if not win: return false

    entry = AntigravityCache[win:id()] or cacheLoadFromDisk()[win:id()]

    # --- Tier 1: fast path ---
    if entry and entry.path:
        candidate = resolvePath(win.AXRoot, entry.path)
        if candidate and isElementValid(candidate, entry.signature):
            press(candidate); entry.axRef = candidate; entry.failCount = 0
            return true
        entry.failCount += 1

    # --- Tier 2: heuristic subtree search ---
    if entry and entry.path and entry.failCount < 3:
        parentHint = resolvePath(win.AXRoot, sliceButLast(entry.path))
        found, path = search(parentHint or win.AXRoot, isSubmitButton, {maxDepth=4, timeoutSec=0.5})
        if found:
            cacheStore(win:id(), path, signatureOf(found))
            press(found); return true

    # --- Tier 3: full traversal ---
    found, path = search(win.AXRoot, isSubmitButton, {maxDepth=14, timeoutSec=2.0})
    if found:
        cacheStore(win:id(), path, signatureOf(found)); cacheFlushToDisk()
        press(found); return true

    # --- Fallback: raw keystroke, last resort ---
    hs.eventtap.keyStroke({"cmd"}, "return")
    notify("Antigravity: button not found, sent raw keystroke fallback")
    return false
```

`isSubmitButton(node)` predicate priority order (most to least reliable):
1. `AXRole == "AXButton"` and `AXDescription`/`AXTitle` matches `"Submit"` or aria-label equivalent exactly.
2. Role is button, sits inside the composer/input container (identifiable by proximity to an `AXTextArea`/`AXTextField` sibling), and is the last enabled actionable button in that container.
3. Role is button with a recognizable icon glyph attribute (Chromium apps often expose `AXTitle` as empty but keep a stable `AXIdentifier`/DOM id if accessibility tree mirrors ARIA attributes — check `AXDOMIdentifier` if present, it's often the most stable of all).

`search()` should be a depth-limited BFS (not DFS) since submit buttons are shallow in the tree relative to page root, and BFS finds shallow matches faster while naturally bounding worst-case time — this matters because the original was described as fast/reliable, and unbounded recursive DFS over an Electron AX tree can take seconds and hang the hotkey.

## 5. Error Handling & Edge Cases

| Failure Mode | Mitigation |
|---|---|
| AX object stale after re-render | Never trust `axRef` alone — path replay + signature check on every use |
| Accessibility permission revoked/not granted | Check `hs.accessibilityState()` at module load; alert user with System Settings deep link if false |
| Multiple Antigravity windows/profiles | Cache keyed by `win:id()`, never global |
| Button temporarily disabled (empty input, streaming in progress) | `isElementValid` checks `AXEnabled == true`; if disabled, don't cache-invalidate, just fall through to keystroke fallback or no-op with a subtle notification |
| App not frontmost when hotkey fires | Guard clause: if `hs.application.frontmostApplication():bundleID()` doesn't match Antigravity's bundle ID, pass the keystroke through natively (`return false` from hotkey callback isn't supported in Hammerspoon — instead re-post the event via `hs.eventtap`) |
| Antigravity ships a UI update that reshuffles DOM/AX tree structure | `failCount` threshold forces Tier 3 full retraversal instead of repeatedly failing Tier 1/2; also expose a manual `hs.hotkey` (e.g. `cmd+shift+r`) to force `cacheInvalidate()` |
| Traversal takes too long and blocks the UI thread | Hard `timeoutSec` cutoff using `hs.timer` wall-clock checks inside the BFS loop, not just depth limits |
| Signature collides with a different button after a UI change | Signature should combine role + normalized title/description + relative sibling-index, not title alone |
