## Audit Summary

The proposed architecture is directionally sound (persistent-queue + sleep-gap-detection + context-gate + silence-as-signal are all correct primitives), but it has several structural weaknesses that will surface specifically on a laptop that sleeps unpredictably, and the Telegram-vs-iMessage decision has a clear technical winner that the plan doesn't fully justify against Matt's stated preference for iMessage/Photon. Below is the critical pass.

## 1. macOS Sleep/Wake & launchd Blind Spots

**The "60-second tick" assumption is the single biggest flaw.** A `launchd` agent with `StartInterval=60` does not run every 60 seconds while the Mac sleeps — it simply does not fire at all during sleep, and on wake `launchd` coalesces all missed intervals into a single run, not one run per missed minute. This actually helps the "avalanche" problem the plan worries about, but it also means the "every execution tick" wall-clock-delta check in the plan can't rely on a live in-process loop that persists across sleep; the process itself is likely not even running. `KeepAlive` will restart a crashed daemon, but it will not keep a process resident and ticking through sleep — the OS suspends it. The plan needs to be explicit that **the daemon is not a continuously-running asyncio loop across sleep**; it is a process that gets killed/suspended at sleep and re-invoked at wake via `StartInterval` + `RunAtLoad`, and *every* invocation must independently rediscover state from SQLite, not from in-memory scheduler state. The current pseudo-code implies persistent memory of `SLEEP_RECOVERY_MODE` across ticks, which won't survive process suspension reliably.

**`StartCalendarInterval` vs `StartInterval` behave differently on wake**, and the plan doesn't specify which it uses. Per Apple's own history and the launchd sources reviewed, `StartCalendarInterval` catches up missed fires on wake (with coalescing of duplicate missed events), while `StartInterval` is more prone to being silently dropped depending on kqueue-based sleep-time accounting. The implementation step should mandate `StartCalendarInterval` with a tight recurring cadence (e.g., every 15 min) rather than `StartInterval`, since `StartInterval`'s sleep-skipping behavior is the more commonly reported failure mode.

**A restart cancels pending wake catch-up.** Multiple sources confirm that if the Mac is *rebooted* (not just slept) while a `launchd` job was pending, the pending fire is forgotten rather than replayed on the next boot. Because the trigger queue lives in SQLite (not in `launchd`'s internal state), this is actually fine for the assistant's own triggers — but it means the daemon cannot depend on `launchd`'s catch-up semantics at all for correctness. The SQLite `trigger_queue` with its own `scheduled_at`/`expires_at` TTL is the correct source of truth; `launchd` should be treated as nothing more than "wake me up periodically, or immediately on boot," never as a reliable delivery mechanism for a specific trigger.

**`defaults read com.apple.ncprefs` for Focus mode is fragile and likely already broken.** Since macOS Ventura, Focus/DND state moved into a binary plist format under `~/Library/DoNotDisturb/DB/` with per-mode configuration files, and Apple has repeatedly changed the schema across OS versions without a public API. A plan that hard-codes a `defaults read` call is a single-OS-update away from silently returning stale or empty data with no error — this needs a documented fallback (e.g., detect stale/missing key and fail *open* to "assume available" or *closed* to "assume busy," and explicitly pick one policy) and version-pinned parsing with a self-test that runs in CI or on daemon startup.

**AppleScript/EventKit calendar queries require the process to have Automation/Calendar permission, and a background `launchd` LaunchAgent invoking `osascript` will frequently trigger the macOS TCC (Transparency, Consent, Control) permission prompt the first time — and if it's denied or the daemon runs headless without an active login session, EventKit access silently returns nothing rather than raising a catchable error.** The plan's "fallback to default routine buffers" mitigation is right in spirit, but it must also **log and surface** permission failures distinctly from "no events found," or you'll never notice the Context Gate has been blind for weeks.

**Silence Watchdog needs a persistent poll of its own**, and the plan currently nests it inside the same tick loop as trigger dispatch. If the Mac sleeps for 6 hours with 3 outbound signals awaiting response, on wake all 3 will time out simultaneously, spike the `low_energy_counter`, and potentially trigger the cooldown suppression rule right as the user becomes available — the opposite of what's wanted. The watchdog needs to treat "no watchdog run occurred while asleep" as a null result, not a decayed-response result, or friction-scoring will be systematically biased by how long the Mac happened to sleep, which is exactly the "silence" signal but for the wrong reason (machine unavailability, not user unavailability).

## 2. Telegram vs. iMessage (Photon / BlueBubbles)

| Dimension | Telegram | iMessage (BlueBubbles) |
|---|---|---|
| Inline buttons / 1-tap callbacks | Native `InlineKeyboardMarkup`, first-class, no extra infra | Not supported by Apple; must be simulated via tap-backs (👍/👎 reactions) which BlueBubbles exposes only with **Private API enabled, which requires disabling SIP** on the host Mac |
| Dynamic message editing | Native `editMessageText`/`editMessageReplyMarkup` | Not supported by iMessage/BlueBubbles at all — messages can't be edited or have their keyboard removed after sending |
| Delivery/push reliability | Long-polling or webhook via stable public Bot API, works from anywhere | Depends on a always-on macOS BlueBubbles Server process on the *same host that's already sleeping intermittently* — a chicken-and-egg problem, since the messaging layer would go down exactly when the host sleeps |
| API stability | Official, versioned, heavily used by thousands of bots | Community reverse-engineered project; frequently breaks across macOS point releases since it reads iMessage's private SQLite `chat.db` and injects into the app process |
| Setup cost | `pip install python-telegram-bot`, a bot token, done | Requires installing BlueBubbles Server, granting Full Disk Access, and disabling SIP for reactions/tapbacks — a meaningfully higher-risk security posture change on Matt's daily-driver Mac |

**Verdict:** Telegram is the clear technical choice for this specific use case, not because iMessage/Photon is a worse *chat experience* generally, but because the two hard requirements — (a) message editing to remove a stale keyboard and show "(Check-in expired)", and (b) tappable inline buttons without a free-text reply — are things Apple's iMessage protocol simply does not expose, even through BlueBubbles's reverse-engineered bridge. BlueBubbles can approximate button-like interaction only via tapback reactions, which requires disabling SIP (System Integrity Protection) on the same host running the assistant, which is a security downgrade disproportionate to the UX gain, and it still can't edit sent messages. Given memory shows Matt already prefers Telegram over Discord for automated notifications, and given the plan's core UX (inline rating buttons, editable "expired" states) is Telegram's bread and butter, keeping Telegram as the interface and treating iMessage/Photon purely as Matt's personal messaging app (unconnected to this system) is the right call. If Photon impressed him as a *client*, that's orthogonal — Telegram also has excellent native macOS/iOS apps, so there's no UX regression from using it as a second, purpose-built channel.

## 3. Simpler Alternative Paths

**Alternative A — Shortcuts + Focus Filters instead of a custom Context Gate.** Rather than parsing `defaults read` or brittle Focus plist files, macOS/iOS Shortcuts can query "Get Current Focus" and calendar availability as first-class Shortcuts actions, invocable via `shortcuts run <name>` from the daemon. This trades a custom AppleScript/EventKit reverse-engineering effort for Apple's own supported automation surface, and is far less likely to break across OS updates, at the cost of a slightly higher per-call latency (~200-500ms shell-out).

**Alternative B — Cron-on-a-cheap-always-on-VPS as source of truth, Mac as pure compute.** Given `ai-os` already runs a VPS with Caddy/Tailscale, the entire trigger-scheduling and silence-watchdog logic (which doesn't need Mac-specific data) could live on the always-on VPS, with only the Context Gate's Calendar/Focus probes needing to run locally on the Mac (via a tiny Tailscale-reachable HTTP endpoint the VPS polls before firing). This eliminates 90% of the sleep/wake-recovery complexity entirely, since the scheduler process never sleeps — only the "is Matt actually free" check needs to reach the Mac, and if the Mac is unreachable, the natural and correct fallback is simply "suppress and retry," which is already the desired behavior for an offline Mac. This is very likely the **more maintainable** path long-term and should be seriously considered as a rewrite of the "run on `launchd`" assumption baked into the current plan.

**Alternative C — Reduce state machine surface by using Telegram itself as the queue.** Rather than maintaining `outbound_signals` timeout logic manually, Telegram's Bot API supports message TTL semantics loosely via scheduled `editMessageText` calls triggered by the same scheduler; no architectural change needed here, but it's worth noting the "friction score" and cooldown logic in `user_dynamics` is the one piece of genuinely novel logic in the whole system — everything else (FSRS math, Telegram delivery, calendar reads) is a wrapper around existing libraries, which validates the original "glue, don't build" instinct from the referenced conversation history. The audit's main recommendation is to keep that philosophy and push the Context Gate's sleep/wake fragility off the laptop entirely (Alternative B) rather than trying to harden `launchd`/AppleScript further, since those are the least controllable, least testable parts of the stack.
