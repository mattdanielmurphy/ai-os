## 1. Architectural Strategy

Implement a global, AI-OS-owned Bun launcher that intercepts `bun dev` and `bun run dev`, runs the original command with the real Bun executable, detects its actual listening server, and registers `<project-name>.test` with puma-dev.

Use a small, session-owned loopback relay between puma-dev and the project server:

```text
Browser → puma-dev → stable session relay → detected project server
                         ↑
                  AI-OS Bun supervisor
```

The **invariant** is that AI-OS adds domain routing without rewriting project scripts, replacing puma-dev, or silently taking ownership of existing mappings.

Puma-dev explicitly supports proxy files in `~/.puma-dev` containing a port or host-and-port, and supports WebSocket proxying. Use that interface rather than symlinking JavaScript projects as Rack applications.  Bun supports both `bun dev` and `bun run dev`, including script lifecycle hooks; launch the original command through real Bun so those semantics remain intact.

### Concrete architectural decisions

1. Install an executable shim named `bun` in an AI-OS-owned directory placed before the real Bun directory in managed `PATH`.
2. Resolve and record the real Bun executable during installation. Never replace or rename the vendor executable.
3. Have the shim invoke the TypeScript supervisor through the recorded absolute real-Bun path, avoiding recursive shim execution.
4. Intercept only confirmed invocations of a package’s `dev` script. Forward other Bun commands unchanged.
5. Run development processes with inherited terminal streams. Do not depend on reading or rewriting server output.
6. Discover listeners belonging to the launched process tree using macOS process/listener inspection.
7. Write puma-dev’s mapping to the relay’s port, not directly to the application’s potentially changing port.
8. Keep the relay port fixed for the lifetime of a session; change its upstream when the application restarts or selects another port.
9. Preserve all unmanaged puma-dev files and symlinks.
10. Implement the launcher, supervisor, relay, configuration tooling, and tests with Bun. Shell is allowed for bootstrap integration; do not introduce Node, npm, pnpm, or Python into this feature.

A global launcher is necessary because adding `predev` scripts would require per-project modifications and cannot supervise the entire development-server lifecycle. Bun does execute lifecycle hooks, but those are project-level behavior, not a global interception mechanism.

### Scope of the guarantee

After one-time global installation:

- `bun dev` and `bun run dev` automatically participate in this convention.
- New projects need no registration command.
- Commands invoking an absolute vendor Bun path bypass the shim intentionally.
- Shells, IDEs, and automation must inherit the managed `PATH`; installation must explicitly test these contexts rather than claiming universal coverage.
- A project must actually start an identifiable local HTTP server. Arbitrary scripts, detached servers, and multi-server projects may require a declaration.

Do not install a second DNS resolver or reverse proxy, replace existing puma-dev configuration, or automatically perform privileged setup.

## 2. Data Structures & State Management

### Project configuration

Use this preferred declaration:

```json
{
  "aios": {
    "devDomain": {
      "enabled": true,
      "name": "daily-mini-crossword",
      "port": 5173,
      "protocol": "http"
    }
  }
}
```

Every field is optional. `port` is a selection hint for an existing server, not an instruction to force the application onto that port.

Support:

```json
{ "aios": { "devDomain": false } }
```

and an explicit `enabled: false`.

Configuration precedence, highest first:

1. Invocation environment:
   - `AIOS_DEV_DOMAIN=off`
   - `AIOS_DEV_DOMAIN=<name>` or `<name>.test`
   - `AIOS_DEV_PORT=<integer>`
2. Explicit `package.json` declaration.
3. `.aios-dev.json` in the resolved package directory, using the same object shape as `devDomain`.
4. User-local per-project override, keyed by canonical package-directory path.
5. Automatic defaults.

Resolve each field independently, but an explicit higher-priority disable always wins. Invalid explicit configuration disables automatic registration for that invocation with a clear warning; it must not silently fall back to another hostname.

Do not read raw `.env` files. Passing the inherited environment to real Bun does not require inspecting or logging its values.

### Naming

Default name selection:

1. Nonempty package `name`.
2. Package-directory basename.

Sanitize automatic names deterministically:

- Unicode-normalize and lowercase.
- Convert a scoped package such as `@matt/daily-mini-crossword` to `matt-daily-mini-crossword`.
- Replace non-ASCII alphanumeric runs with `-`.
- Trim leading and trailing hyphens.
- Use `project-<short-path-hash>` if the result is empty.
- Limit the DNS label to 63 characters; append a stable path hash when truncating.
- Append `.test` only for display and requests, not for the puma-dev filename.

Explicit names accept a single valid DNS label, optionally followed by `.test`. Reject paths, whitespace, wildcards, other suffixes, and nested subdomains in v1. Do not silently sanitize an explicit override.

### Persistent and runtime state

Use:

```text
~/.config/ai-os/dev-domains/config.json
~/.local/state/ai-os/dev-domains/
  registry.json
  locks/
  sessions/<session-id>.json
```

Keep these directories private to the user.

Define:

```text
GlobalConfig
  schemaVersion
  realBunPath
  enabled
  projectOverrides
  discoveryTimeoutMs = 60000

ProjectConfig
  enabled
  name
  port?
  protocol = "http"

SessionRecord
  schemaVersion
  sessionId
  canonicalProjectRoot
  domain
  supervisorPid
  supervisorStartIdentity
  childPid
  startedAt
  relayAddress
  upstream?
  mappingPath
  mappingFileIdentity
  mappingContentHash
  state
  lastDiagnostic?

Upstream
  address
  port
  protocol
  owningPid
  processStartIdentity

SessionState
  starting | discovering | ready | degraded | stopping | stopped
```

Store no credentials or application response bodies.

### Ownership and concurrency

- Acquire an exclusive domain lock before publishing a mapping.
- Use atomic lock-directory creation and atomic state-file replacement.
- Validate PID plus process-start identity before declaring a session stale.
- Create mappings exclusively; never overwrite an existing unmanaged entry.
- Record mapping inode/file identity and exact content.
- Remove a mapping only if its identity and content still match the session’s record.
- If someone replaces or modifies the mapping, relinquish management and leave their version untouched.

A second active invocation for the same domain must continue running its dev script but receive a routing-conflict warning. Do not hijack the first session.

## 3. API / Interface Contracts

Use a modular TypeScript implementation with these responsibilities and signatures:

| Interface | Contract |
|---|---|
| `classifyInvocation(argv, cwd): InvocationDecision` | Returns pass-through or intercepted dev-script execution; resolves Bun’s effective package directory. |
| `resolveRealBun(config, shimPath): Promise<string>` | Returns a valid non-shim executable; rejects recursion and stale installation paths. |
| `resolveProjectConfig(context): Promise<ResolvedProjectConfig>` | Applies precedence, validates declarations, and supplies diagnostic provenance. |
| `deriveDomain(packageName, projectRoot, explicitName?): Domain` | Produces validated hostname and mapping basename. |
| `acquireDomainLease(domain, session): Promise<LeaseResult>` | Distinguishes acquired, active conflict, stale-owned state, and unmanaged mapping. |
| `spawnOriginalDev(realBun, argv, context): ChildHandle` | Preserves argv, cwd, environment, lifecycle hooks, stdin/stdout/stderr, and terminal behavior. |
| `discoverProcessTree(rootPid): Promise<ProcessIdentity[]>` | Enumerates descendants without identifying processes by name alone. |
| `discoverListeners(processes): Promise<ListenerCandidate[]>` | Collects TCP listeners with PID attribution and compatible loopback addresses. |
| `selectUpstream(candidates, config): Promise<DiscoveryResult>` | Returns selected, waiting, ambiguous, or unsupported; never guesses between distinct HTTP servers. |
| `startRelay(): Promise<RelayHandle>` | Binds an ephemeral loopback port and exposes `setUpstream`, `clearUpstream`, and `close`. |
| `publishMapping(lease, relay): Promise<OwnedMapping>` | Publishes the puma-dev proxy file under exclusive ownership. |
| `verifyRoute(domain, relay, upstream): Promise<RouteStatus>` | Separately checks application reachability and hostname routing. |
| `cleanupSession(session): Promise<void>` | Idempotently releases only owned resources. |

### Invocation parser requirements

Support and test:

- `bun dev`
- `bun run dev`
- Script arguments and `--` forwarding.
- Bun options before the script, including supported cwd selection.
- Bun runtime flags without moving them or passing them to the wrong layer.

Bun distinguishes runtime flags from script arguments by position, so the shim must preserve their placement.

If a Bun option cannot be safely interpreted, pass through unchanged with a concise diagnostic for dev-like invocations. Do not build a parser that accidentally intercepts `bun test`, `bun install`, `bunx`, or a source file named `dev`.

Verify actual package resolution against the installed Bun version, including workspaces. Do not implement an approximate “nearest package.json” rule without compatibility tests.

### Relay contract

Implement a transparent streaming TCP relay:

- Listen on `127.0.0.1` only.
- Accept puma-dev connections and connect to the current selected upstream.
- Preserve the byte stream; do not rewrite HTTP headers or buffer entire responses.
- Support backpressure, half-close, connection errors, and streaming.
- Close all active upstream connections when upstream identity changes.
- Return a small HTTP 503 response when no upstream is available.
- Default to plain HTTP upstreams.
- For explicitly configured HTTPS upstreams, implement verified TLS or report unsupported; never silently disable certificate validation.

Transparent forwarding preserves the host and upgrade requests rather than introducing a second HTTP application proxy. Puma-dev already supplies domain proxying and WebSocket support.

## 4. Logic Flow & Algorithms

### Global installation

```text
inspect existing AI-OS installation and shell-management conventions
locate real Bun before activating shim
validate Bun version and executable identity
inspect puma-dev presence and existing routing setup
write managed launcher configuration
install shim in AI-OS-owned PATH directory
integrate directory using existing managed PATH mechanism
test fresh-shell resolution
run doctor
```

Keep installation reversible. Report missing DNS, certificate, or daemon setup without performing privileged changes automatically.

### Intercepted development execution

```text
classify original invocation
if not a supported dev-script invocation:
    exec real Bun with original arguments

resolve configuration and project identity
if disabled:
    exec real Bun unchanged

create session record
attempt domain lease
if lease unavailable or routing setup fails:
    warn
    run real Bun normally without routing
    preserve its exit status

start relay
publish owned puma-dev mapping to relay port
spawn real Bun with original argv and inherited terminal streams

while development process is alive:
    periodically enumerate its process tree
    inspect attributed TCP listeners
    apply explicit port selector, if present
    probe candidate listeners for HTTP compatibility
    distinguish duplicate address bindings from distinct servers

    if exactly one eligible endpoint:
        update relay upstream when identity changes
        verify hostname route
        announce URL once ready

    if none:
        keep waiting; clear a dead upstream

    if multiple:
        keep relay unavailable
        print one actionable ambiguity diagnostic

on child exit or shutdown:
    close relay
    remove mapping only if still owned
    release lock
    remove active session state
    propagate original child exit result
```

### Port detection

Poll every 250 ms during startup, backing off to 1 second after readiness.

Use `/bin/ps` and `/usr/sbin/lsof` through absolute paths. Prefer lsof’s machine-readable field output; do not parse aligned human-readable columns.

Selection rules:

1. Accept only listeners attributed to the launched process tree.
2. Convert wildcard listeners to a reachable loopback address.
3. Reject externally bound-only listeners.
4. If an explicit port exists, filter by that port.
5. Probe using the intended `<name>.test` Host header.
6. Treat a syntactically valid HTTP response, including 4xx/5xx, as evidence of HTTP—not proof of application health.
7. Collapse IPv4/IPv6 bindings for the same server where their identity is demonstrably equivalent.
8. Select only when one distinct eligible server remains.

Never scan arbitrary localhost ports or adopt an unrelated process merely because it occupies a configured port.

At the 60-second discovery threshold, print a diagnostic and continue monitoring at the slower interval. Slow startup must not terminate the dev command.

### Signals and terminal semantics

Treat this as a release-blocking compatibility area:

- Keep the foreground terminal relationship intact.
- Preserve interactive stdin and terminal-sized output.
- Avoid blindly forwarding Ctrl-C if both supervisor and child already receive the terminal’s foreground-group signal.
- Forward signals delivered only to the supervisor without double delivery.
- Restore terminal state and clean up after interruption.
- Match native Bun exit behavior, including signal termination.

Inspect the existing PTY/process utilities, but do not introduce a PTY unless tests show it is needed. An unnecessary PTY can change output, input, and job-control behavior.

## 5. Error Handling & Edge Cases

| Situation | Required behavior |
|---|---|
| Puma-dev absent or unreachable | Run the dev command normally; report domain routing unavailable. |
| Existing unmanaged file or symlink | Preserve it; require an explicit different name or manually managed migration. |
| Concurrent same-domain session | Preserve the first session; second command continues without automatic routing. |
| Sanitized-name collision | Report both project identities; require an override. Do not silently rename one. |
| Port auto-increments because preferred port is occupied | Detect the actual attributed listener and route to it. |
| Multiple HTTP servers | Require `port`; do not infer frontend versus API by lowest port. |
| Non-web dev command | Continue normally; report that no HTTP listener was identified. |
| Detached server | Do not adopt automatically. State the limitation and require a separately managed integration. |
| Server restart or changed port | Update upstream while keeping the relay mapping stable. |
| Host allowlist rejects `.test` | Diagnose the rejection; offer a framework-specific, narrow allowlist change. |
| HMR uses an incorrect host or port | Diagnose and configure only the representative framework’s public HMR endpoint. |
| HTTPS upstream with untrusted certificate | Require trust configuration; never use an insecure bypass by default. |
| Supervisor killed abruptly | Next `doctor` or invocation reclaims only verifiably stale owned state. |
| User changes mapping while running | Stop managing that mapping; preserve the user’s change. |
| Corrupt ownership metadata | Fail closed for mapping modification; continue the original dev command. |
| Bun upgrades move the executable | `doctor` identifies and repairs the recorded path through explicit installation tooling. |

Do not use `allowedHosts: true`, disable origin protection globally, or inject framework-specific flags into all projects. Puma-dev’s WebSocket support does not remove application-level host/origin restrictions.

The relay also avoids relying on immediate puma-dev remapping when a server port changes. Validate installed puma-dev behavior during integration tests; do not restart the shared daemon during every project launch.

## Acceptance Criteria

The implementation is complete only when:

- A newly created eligible project becomes reachable at its derived `.test` hostname using only `bun dev`.
- The standard works across projects, not just the representative application.
- Explicit declarations and opt-outs behave deterministically.
- Original Bun script execution, hooks, arguments, terminal interaction, and exit behavior are preserved.
- Port discovery uses process ownership rather than guesses.
- Restarted servers can change ports without recreating their puma-dev mapping.
- Existing puma-dev mappings remain untouched.
- Routing failures do not prevent the original development command from running.
- HMR/WebSockets and safe real-project verification have documented results.
- Installation and uninstall are reversible, and the implementation introduces no non-Bun JavaScript toolchain.
